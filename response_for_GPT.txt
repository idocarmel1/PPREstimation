Overall verdict
---------------
The review is competent and mostly accurate. It correctly read the code (the
descriptions of _collapse_det_scaling and the (I-B)x=c system match reality).
The strongest, most actionable points are #4 (symbolic path ignores stability),
#7 (pooled-scaling numerator/denominator inconsistency), and the "don't silently
return negatives" thread in #12. The weakest are #8/#9 (ecologically interesting
but speculative, no data) and parts of #3 (the proposed fix is cleaner but, for
this code, largely equivalent to what's already there). Details below, point by
point, with an honest "agree / partly / disagree" and a priority.


1. collapse_det as a fallback  --  AGREE
   - GPT's reading of _collapse_det_scaling is correct: it sums the DET basis
     columns, solves the 1-D self-consistency x = a + b*x, and multiplies every
     DET column by the same scalar. It does NOT structurally rebuild the web.
   - The naming critique is fair: calling it "collapse" overstates it. It is
     "pooled scaling," exactly as GPT says. Renaming to det_resolution=
     "pooled_scaling" in any diagnostics is a good, cheap clarity win.
   - b < 1 really is the 1-D analogue of spectral_radius(B) < 1, and the code
     already raises when b >= 1 (L1082). Good.
   PRIORITY: low (cosmetic/naming), but worth doing for the paper.

2. Mode instead of Boolean (never/auto/always)  --  AGREE, with a caveat
   - Good API. But note a real behavioral gap GPT only half-flags: TODAY,
     collapse_det=False does NOT mean "never + raise on instability." It means
     "always call np.linalg.solve and return whatever comes out" (L1204-1207,
     L1229-1232) -- including SILENTLY NEGATIVE values. So GPT's "never" mode
     (which RAISES on rho>=1) is strictly safer than current False. That's the
     actual bug worth fixing, more than the enum itself.
   - Backward-compat mapping True->"auto" is the right call.
   PRIORITY: medium. The enum is nice-to-have; the "never must raise, not
   silently return negatives" behavior change is the substantive part.

3. Check spectral_radius(B) directly  --  PARTLY AGREE (smaller win than implied)
   - Current check: min(real(eigvals(I-B))) <= 0, i.e. max(real(eigvals(B))) >= 1.
   - For a NONNEGATIVE B, Perron-Frobenius makes the dominant eigenvalue real and
     positive, so max|lambda(B)| == max Re(lambda(B)) and the two tests coincide.
     GPT concedes this ("often catches the same problem, but indirect"). So the
     rho = max|eig(B)| rewrite is cleaner/clearer but NOT a correctness fix on its
     own.
   - The genuinely new value in #3 is the CONDITION-NUMBER guard: rho can sit at
     0.999 (near-singular I-B) and the current test passes while the solution is
     numerically huge / ecologically useless. Adding cond(I-B) > threshold is a
     real robustness improvement.
   - CAVEAT GPT missed: is B actually guaranteed nonnegative here? B[l,j] =
     m_l @ SPPR[:,det_j], with m_l = M0/q_l >= 0. But SPPR columns come from a
     sympy nullspace + rref normalization; rref basis vectors are not guaranteed
     sign-definite. If any SPPR detritus-basis entry is negative, B has negative
     entries, Perron-Frobenius no longer guarantees the dominant eigenvalue is the
     real positive one, and BOTH the current test and a naive rho test can behave
     unexpectedly (complex dominant eigenvalues). This is worth empirically
     checking on the real models before trusting either criterion. If B can be
     negative, the direct |lambda| test is actually the safer choice -- which
     strengthens GPT's recommendation for a different reason than GPT gave.
   PRIORITY: medium. Adopt rho = max|eig(B)| + cond guard, AND verify B's sign
   on real data.

4. Make SPPR_symbolic match SPPR_new  --  STRONGLY AGREE (best catch)
   - Confirmed: in both symbolic helpers (L1322, L1442) collapse is triggered by
     `collapse_det and len(DET_seq) > 1 and TE_option in ('GE','With Egestion')`
     with NO stability check at all. A perfectly stable multi-detritus model is
     collapsed unconditionally whenever collapse_det=True. That is inconsistent
     with the numeric path, which only collapses when the eigen-test fails.
   - One nuance GPT understates: the symbolic path does not build a numeric B --
     it gets the exact detritus scaling from sympy linsolve (sol_dict2). So you
     cannot trivially "call the same solve helper." What you CAN and SHOULD share
     is the stability GATE: build B/c numerically (or read rho off the symbolic
     solution), decide solve-vs-collapse with the SAME criterion, then let each
     path apply it. Full unification of the solver is harder than GPT implies;
     unifying the decision is easy and is the real fix.
   PRIORITY: high. This is a correctness/consistency bug, not a style issue.

5. Store diagnostics  --  AGREE
   - Today the instance records nothing about which path ran. For a reproducible
     paper this matters. self.detritus_resolution_info{ method, reason, rho_B,
     cond, det_names, collapse scalar } is cheap and sensible.
   PRIORITY: medium (important for the manuscript, not for correctness).

6. Missing det_fate columns should not receive all detritus  --  AGREE in
   principle, but it's an edge case, and "give 0" may not be the right default
   - Confirmed the whole-flow fallback in all four places GPT names:
       apply_ecopath_defaults L269-270  -> df['flow_to_det'].sum()
       get_Z                  L584-585  -> Z.loc[det_j,:] = flow_to_det
       get_TL (GE)            L671-672  -> (M0)/flow2det
       SPPR_new _get_m_l      L1180     -> M0/q_l  (implicitly fracs=1 everywhere)
   - GPT is right that in a multi-detritus model this mis-attributes the entire
     detritus flow to a pool that nothing actually feeds.
   - BUT: in a well-formed det_fate matrix EVERY DET group is a column, so this
     branch should never fire in correct data. A missing column usually signals a
     malformed/incomplete det_fate, not a legitimate "zero-inflow" pool. So I'd
     push back slightly on silently substituting 0 -- that can mask a data error.
     Better: in the multi-DET case, RAISE or warn on a missing det_fate column,
     and only zero-fill if the user explicitly opts in. The defensive instinct is
     right; silent 0 vs silent whole-flow are both silent.
   - Minor: in apply_ecopath_defaults the whole-flow fallback inflates q_det_j,
     which makes b SMALLER (more "stable"), so it doesn't cause spurious
     instability -- it causes wrong attribution. Worth saying so the severity is
     judged correctly.
   PRIORITY: low-medium, contingent on whether real models ever have incomplete
   det_fate. Verify before changing.

7. Include detritus-fate sums in pooled scaling  --  AGREE (real inconsistency)
   - This one is technically correct and subtle. In _collapse_det_scaling:
       q_combined = sum_j q[det_j]   and   m_combined = M0 / q_combined.
     Each q[det_j] was built in apply_ecopath_defaults as
       (flow_to_det * det_fate[det_j]).sum(),
     i.e. q_combined = flow_to_det . (sum_j fate_j). So the DENOMINATOR is
     fate-weighted while the NUMERATOR (M0) is the full amount. If every fate row
     sums to 1, q_combined == total flow_to_det and it's consistent. If fate rows
     sum to < 1 (burial / export / untracked loss), q_combined < total flow and
     m_combined is inflated -- exactly GPT's point. Multiplying M0 by
     fate_to_modeled_det = sum_j fate_j restores numerator/denominator
     consistency.
   - So the fix is justified IF the models actually encode fate rows summing < 1.
     ACTION: check whether real_models det_fate rows sum to 1 or < 1. If always 1,
     this is a no-op safety guard; if < 1 occurs, it's a genuine correction.
   PRIORITY: medium. Implement with the >1 validation GPT suggests; gate the
   behavior change on the empirical fate-sum check.

8. B_open / burial / mineralization / dilution  --  INTERESTING, BUT SPECULATIVE
   - The math is sound: nonnegative B_open with spectral_radius < 1 gives a finite
     nonnegative Neumann series I + B_open + B_open^2 + ...; both 8A (damp B only,
     B_open = diag(1-loss) B, c unchanged) and 8B (dilute source,
     B_open = diag(theta) B, c_open = diag(theta) c) are legitimate and
     ecologically distinct.
   - The problem is DATA, not code: this needs per-detritus burial / export /
     external-input / theta parameters the project does not currently have. Coding
     det_open_mode + five new per-detritus parameter vectors speculatively, with
     no data to populate them, adds surface area and a tuning knob that can make
     instability "go away" without justification -- a reviewer-bait risk for the
     paper.
   - Recommendation: treat #8 as a documented FUTURE option, not part of this
     change. If you DO want it, 8B (source dilution / theta) is the more defensible
     interpretation for benthic Ecopath detritus, as GPT says, and theta can in
     principle be read from the same det_fate / import structure rather than
     invented. Start there only if you have or can derive theta.
   PRIORITY: low for now (research decision, not a bug). Revisit if a model truly
   has rho>=1 AND you have loss/import data.

9. Relationship collapse_det vs B_open  --  AGREE conceptually
   - The framing (collapse = lower resolution but robust; B_open = keep resolution
     but needs assumptions) is correct and useful. The suggested hierarchy
     (try open if params given -> raw multi-det -> pooled in auto / raise in
     never -> raise if even pooled fails) is reasonable. Just don't build the
     B_open rungs until #8's data exists; the rest of the hierarchy is implementable
     today.

10. Implementation plan  --  AGREE with scope-trim
   - _spectral_radius helper, det_collapse_mode enum, and the test suite (A-G) are
     all worth doing and low-risk. Tests A-G are good regardless of which other
     changes land -- I'd write them FIRST, since they pin current behavior (Test A:
     one-DET matches old) and expose the #4 inconsistency immediately (Test B: a
     stable two-DET model should NOT collapse in auto -- the symbolic path fails
     this today).
   - Skip Step 4 (_apply_detritus_openness) for now (see #8).
   - Be realistic about Step 6: "make symbolic call the same solve" is partly
     blocked by sympy-vs-numpy solving (see #4). Share the decision, not the solver.

11. Paper method text  --  AGREE
   - The spectral_radius(B) < 1 wording is correct and publishable. Use the first
     paragraph now. Hold the B_open paragraph until/unless #8 is actually
     implemented and parameterized -- don't describe a method you didn't run.

12. Bottom line  --  MOSTLY AGREE
   - "Don't clip negatives to zero" -- agreed, and worth stating clearly that the
     code does NOT currently clip; it SILENTLY RETURNS negatives when
     collapse_det=False and rho>=1. That silent path is the single most important
     thing to fix: add a negativity / stability guard that either raises (never)
     or falls back (auto). This is independent of all the API/enum cosmetics.
